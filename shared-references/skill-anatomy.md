# Skill 解剖学 — 结构规范、健康判据与设计原理

> 本文档是 skill 结构/原理的知识底座，供三个子 skill 共享引用：
> - **sm-analyzer**（③ 分析）：拆解外部 skill 时，按此文档判断其结构是否规范、设计是否合理
> - **sm-writer**（④ 编写）：起草新 skill 时，按此文档的规范产出并自检
> - **sm-optimizer**（⑤ 优化）：诊断已有 skill 时，按此文档定位结构问题
>
> 第 3 节的健康判据与 `scripts/inventory.py` 的健康检查**一一对应**——脚本按此文实现，此文判据以"机器可检查"为限。

## 1. 目录结构规范

一个 skill = 一个目录。目录名即 skill 的全局标识，必须与 frontmatter 的 `name` 一致（见 §2、§3.4）。

```
my-skill/
├── SKILL.md            # 必需 — 唯一入口
├── references/         # 可选 — 深度细节文档
│   └── topic.md
├── scripts/            # 可选 — 确定性操作脚本
│   └── helper.py
└── assets/             # 可选 — 模板/静态资源
    └── report.html
```

| 单元 | 必需性 | 目的 | 要点 |
|---|---|---|---|
| `SKILL.md` | 必需 | Agent 唯一保证会读的文件：frontmatter（路由信号）+ 最小工作流 | 缺失即 `missing_skill_md` |
| `references/` | 可选 | 承接 SKILL.md 装不下的深度细节，按需加载 | 只有一层，不嵌套子目录 |
| `scripts/` | 可选 | 确定性操作（枚举/校验/渲染），结果可复现 | stdout 只输出机器可读结果，人话解读交给 LLM |
| `assets/` | 可选 | 非指令性资源（模板、样例数据） | 不含可执行逻辑 |

要点：

- **SKILL.md 是契约**。Agent 加载 skill 时唯一保证读取的就是它，其余一切靠它内部的链接引导。
- **可选目录按需创建**，不预建空目录——没有脚本就没有 `scripts/`。
- **references/ 保持扁平**（一层深）。引用文件应能直接解决 Agent 当前的疑问，而不是再引向下一层。

## 2. frontmatter 规范

SKILL.md 顶部必须是 `---` 围起来的 YAML 头：

```yaml
---
name: my-skill
description: 一句话说清做什么。Use when 用户提到 X、Y、Z 时使用。
allowed-tools: Bash, Read    # 可选
---
```

| 字段 | 必需性 | 规则 | 违反后果 |
|---|---|---|---|
| `name` | 必需 | 与目录名**完全一致**（字符串精确比较） | 不一致 → `name_mismatch` |
| `description` | 必需 | ≤1024 字符；触发词内嵌其中（写法见 §5） | 键缺失 → `frontmatter_broken`；超长 → `desc_too_long` |
| `allowed-tools` | 可选 | 限定 skill 可用的工具列表；用不到就不写 | 高危通配（如放开任意命令执行）属安全问题，归 scanner 管 |

`frontmatter_broken` 的两种形态：

1. **围栏缺失**——首行不是 `---`，或找不到闭合的 `---`，解析器拿不到 YAML 边界
2. **键缺失**——YAML 解析成功，但 `name` 或 `description` 键不存在

注意区分：`name` 键**存在但与目录名不一致**不算 broken，单算 `name_mismatch`（§3.4）。

## 3. 健康判据清单（与 inventory.py 一一对应）

inventory.py 对每个枚举到的 skill 目录做以下四项机器检查。判据在此冻结：脚本实现以本节为准；sm-writer 落盘前、sm-optimizer 诊断时，逐条对照本节。

### 3.1 missing_skill_md — 目录缺 SKILL.md

- **判据**：skill 目录下不存在 `SKILL.md` 文件
- **合集豁免（两层枚举）**：目录自身无 SKILL.md、但其二层子目录里有含 SKILL.md 的，该目录是**合集目录**（类目式 `engineering/brainstorming/` 或分步式 `shendu-yuedu/01-init/`），不枚举、不报本 issue——inventory.py 按两层枚举语义处理：一层含 SKILL.md 即 skill 不再下探，二层无 SKILL.md 的目录不再下探（v1 上限两层），仅当两层内均无任何 SKILL.md 才落到本判据
- **为什么是问题**：没有入口文件，Agent 无法加载该 skill，等于没装
- **修复**：补写 SKILL.md（frontmatter + 最小工作流）；若目录本是残留物，建议用户清理

### 3.2 frontmatter_broken — frontmatter 解析失败

- **判据**：SKILL.md 存在，但满足任一：
  - `---` 围栏缺失或不闭合
  - `name` 或 `description` 键缺失
- **为什么是问题**：路由信号（description）不可用或不可信，Agent 无法判断何时触发
- **修复**：补齐围栏与必需键。常见成因是手工编辑时误删

### 3.3 desc_too_long — description 超 1024 字符

- **判据**：`len(description) > 1024`
- **为什么是问题**：超出加载器阈值后，靠后的触发词会被截掉，等于白写
- **修复**：按 §5 公式重写——压缩形容词与实现细节，保住"做什么 + 触发词"

### 3.4 name_mismatch — frontmatter name ≠ 目录名

- **判据**：`name` 键存在，但其值与目录名不一致
- **为什么是问题**：声明名与实际位置脱节导致引用混乱——盘点时重复计数、更新时改错对象
- **修复**：二选一对齐，通常以目录名为准改 frontmatter（目录名往往已被外部路径引用）

## 4. 渐进式披露原则

**核心思想**：Agent 每次触发 skill 都要通读 SKILL.md。入口文件只装"80% 场景够用的最小工作流"，其余细节下沉到按需加载的 `references/`——省 token，也避免 Agent 在枝节条件上过度发挥。

### 4.1 行数上限：SKILL.md ≤200 行

- 本项目统一标准 **200 行**（社区起源是 100 行上限；本合集形态含路由表与协作约定，放宽到 200）
- 经验分布：单一动作型 skill 50 行内；2-3 个工作流的中型 skill 100-150 行；贴着 200 行的通常该拆了

### 4.2 下沉规则

1. 写完 SKILL.md，数行数
2. 超限 → 找出最大的非核心章节（通常是详尽示例、边角场景、长表格）
3. 移到 `references/<topic>.md`
4. 原地留 1-2 行指针：`详见 [references/topic.md](references/topic.md)`
5. 重复直到 ≤200 行

### 4.3 反模式

| 反模式 | 症状 | 后果 |
|---|---|---|
| 完整手册塞入口 | SKILL.md 300+ 行 | 每次触发付全量 token；Agent 过度条件化 |
| 引用汤 | references/ 下 20 个文件 | Agent 分不清该读哪个 |
| 循环引用 | A.md → B.md → A.md | Agent 打转 |
| 入口零示例 | "示例见 EXAMPLES.md" | 最常用的信息也要多加载一层才能动手 |

## 5. description 与触发词写法

**description 是 Agent 决定加载哪个 skill 的唯一信号**——系统提示里并排躺着所有已装 skill 的 description，Agent 靠它路由。它不是营销文案，是路由信号：每个词都在与其他 skill 的 description 竞争触发注意力。

### 5.1 公式：做什么 + 何时用

- **第一句：做什么**。动词开头 + 具体对象，不用形容词
- **第二句：何时用**。`Use when ...`，内嵌触发词

触发词 = **用户会说的原话**。用户不会说"进行文档处理"，会说"提取 PDF 表格"——描述里的词必须与用户的自然用词重叠。

### 5.2 避免与通用词冲突

通用词（"优化"、"写文档"、"分析"）几乎每个 skill 都想抢：写了等于没写，还会误触发。对策：

- 用**具体名词**替换泛称（"PDF 表格"而非"文档"；"改 skill"而非"优化"）
- 用**命名空间前缀**隔离：本项目五个子 skill 全部用 `sm-` 前缀（sm-writer / sm-optimizer / ...），正是为了让触发信号与用户已装的其他 writer / optimizer 类 skill 不相撞，再由路由表用场景短语细分

### 5.3 示例

好（动词前置 + 具体对象 + 显式触发词）：

```
提取 PDF 文本与表格、填写表单、合并文档。Use when 用户提到 PDF、表单、文档提取。
```

坏（无信息量，无法路由）：

```
帮助处理文档。
```

坏（另一种坏：形容词堆砌，无触发词）：

```
全面、强大、现代化的文档处理方案，支持多种格式与场景。
```

### 5.4 长度策略

上限 1024 字符（§3.3），但**短比长好**——多数 skill 100-300 字符足够。需要篇幅时的优先级：

1. 动词 + 对象（做什么）——不可压缩
2. 触发句（何时用）——不可压缩
3. 触发词的多样说法——有余量再扩
4. 反触发（"不做什么"）——仅当存在易混淆的兄弟 skill 才写

## 6. 工作流设计模式

### 6.1 步骤清单化 + 进度勾选

复杂流程写成编号步骤 + 复选框，Agent 执行时逐项勾选追踪：

```markdown
1. [ ] 读 agents.yaml 确定扫描范围
2. [ ] 运行 inventory.py --json
3. [ ] 解读 JSON（清单/重复/健康）
4. [ ] 给出建议
```

每个步骤一句话说清"做什么"，不展开"怎么做"——怎么做属于 references/。创建类流程遵循同一思想的访谈-起草-复核三段式：先问需求（一次一问）、再起草、最后与用户复核后才落盘。

### 6.2 三原则（本项目总协议）

1. **脚本做确定性事**：枚举、校验、渲染、统计——结果必须可复现的操作交给 `scripts/`。省 token，且不会每次生成略有差异的代码
2. **LLM 做判断事**：解读数据、权衡方案、撰写分析、降误报——需要语义理解的操作留给 Agent
3. **危险操作必须确认**：写文件、删文件、改配置之前，先向用户展示将要做什么，确认后再动手。宁可多问，不可先斩后奏

### 6.3 边界判断示例

| 操作 | 归属 | 理由 |
|---|---|---|
| 枚举目录、解析 frontmatter | 脚本 | 确定性，规则明确 |
| 触发词是否精准、描述是否达意 | LLM | 语义判断 |
| 渲染 HTML 报告 | 脚本 | 模板替换，可 golden file 对比 |
| 判断扫描结果是否误报 | LLM | 需要上下文理解 |
| 覆盖写入用户文件 | 确认后执行 | 危险操作 |
