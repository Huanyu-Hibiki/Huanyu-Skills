# Skill 优化审查清单 — sm-optimizer 四维诊断

> 本清单是 sm-optimizer（⑤ 优化）的诊断基线：读目标 skill 后，按四个维度逐项检查，产出按影响排序的问题列表，再进入计划 → 确认 → 修改环节。**先审查，后动手**——未获用户确认前，不修改目标 skill 的任何文件。
>
> 结构判据的权威定义在 [skill-anatomy.md](../../shared-references/skill-anatomy.md)（下文以 § 编号引用）：本清单负责"怎么查"，它负责"什么算合规"。触发准确性如何用测试集验证，见 [eval-notes.md](eval-notes.md)。

## 使用原则

- 按需检查，不必穷举。用户指定优化方向时，先覆盖对应维度，不擅自升级为全量重构
- 判定口径：`通过`（清楚稳定，可直接复用）/ `存疑`（基本可用但有风险）/ `不通过`（影响触发、正确性或安全，须优先修）
- 机器可查的四项健康判据（缺 SKILL.md / frontmatter 残缺 / desc 超长 / 命名不一致）直接跑 `inventory.py`，判据见 skill-anatomy §3——本清单聚焦机器查不了的语义层

## 维度一：触发语义

description 是 Agent 路由的唯一信号（skill-anatomy §5）。查它，就是查"用户说某句话时，Agent 能不能找到这个 skill、且不被兄弟 skill 抢走"。

检查项：

- [ ] `name` 与目录名完全一致（判据 skill-anatomy §3.4）
- [ ] description 第一句说清"做什么"：动词开头 + 具体对象，无形容词堆砌（§5.1）
- [ ] description 第二句说清"何时用"：`Use when ...` 内嵌触发词（§5.1）
- [ ] 触发词是**用户会说的原话**，不是书面语——用户说"改 skill"，不说"进行技能迭代优化"（§5.1）
- [ ] description ≤1024 字符，且无通用词裸奔："优化""分析"这类词必须加具体对象限定（§3.3、§5.2）
- [ ] 与兄弟 skill 边界清晰：负例测试通过——构造 3 条应触发 + 1 条不应触发的话术逐一走查（构造法见 [eval-notes.md](eval-notes.md)）

常见病症与修法：

| 病症 | 症状 | 修法 |
|---|---|---|
| 触发词埋正文 | description 只写"做什么"，触发词藏在正文里 | 把触发词回收到 description（§5.1） |
| 通用词抢触发 | "帮助处理各种文档"式泛描述，谁都可能触发 | 换具体名词；易撞时加命名空间前缀（§5.2） |
| 营销腔 | "全面、强大、现代化"，无信息量 | 按"做什么 + 何时用"公式重写（§5.3 有好坏对比示例） |

## 维度二：工作流可靠性

工作流是 SKILL.md 的主体。查它，就是查"Agent 照着执行，能不能每步都走对、走岔了知不知道、危险处停不停"。

检查项：

- [ ] 步骤编号有序，每步一句话说清"做什么"，不展开"怎么做"（skill-anatomy §6.1）
- [ ] 步骤可执行无歧义：无"适当处理""视情况而定""灵活把握"类软化措辞
- [ ] 失败分支显式：缺文件 / 命令失败 / 空结果 / 目标不存在，每个外部依赖点有"如果 X 失败 → 做 Y"的交代
- [ ] 危险步骤（写 / 删 / 覆盖文件）有确认门槛，且门槛是硬性的——"建议先确认"不算门槛，"未确认前禁止动手"才算（§6.2 原则三）
- [ ] 多步流程（≥4 步）有进度追踪：checkbox 清单，执行时逐项勾选（§6.1）

常见病症与修法：

| 病症 | 症状 | 修法 |
|---|---|---|
| 只写正向路径 | 从头到尾没有一句"如果失败" | 每个外部依赖点补 if-then 分支 |
| 软化措辞 | "建议 / 可以考虑 / 视情况"遍布 | 改为具体动作与参数 |
| 确认门槛名存实亡 | 危险步骤只靠"建议确认"措辞卡 | 显式写出禁止条件与可接受的确认语 |

## 维度三：资源组织

查它，就是查"入口够不够瘦、细节放没放对地方、确定性操作有没有交给脚本"。

检查项：

- [ ] SKILL.md ≤200 行；贴着上限的通常该拆了（skill-anatomy §4.1）
- [ ] 非核心细节已下沉 `references/`，原地留 1-2 行指针（§4.2 下沉规则）
- [ ] 无引用汤：`references/` 文件数适中，SKILL.md 写明"何时读哪个"（§4.3）
- [ ] 无循环引用：A.md → B.md → A.md 会让 Agent 打转（§4.3）
- [ ] 入口不缺最常用示例："示例见 EXAMPLES.md" 把高频信息推远了一层（§4.3）
- [ ] `scripts/` 若存在，stdout 只输出机器可读结果，人话解读交给 LLM（§6.2 原则一）
- [ ] 确定性操作（枚举 / 校验 / 渲染 / 统计）已脚本化，不靠 LLM 每次现写（§6.2、§6.3 边界判断表）

常见病症与修法：

| 病症 | 症状 | 修法 |
|---|---|---|
| 完整手册塞入口 | SKILL.md 300+ 行，每次触发付全量 token | 按 §4.2 五步下沉，直到 ≤200 行 |
| 三种披露反模式 | 引用汤 / 循环引用 / 入口零示例（§4.3 反模式表） | 对照该表逐一对号，缺索引补索引，缺示例搬回入口 |
| 该脚本化没脚本化 | Agent 每次触发都现写同样的枚举 / 渲染代码 | 封装进 `scripts/`，SKILL.md 只留调用方式 |

## 维度四：安全边界

查它，就是查"这个 skill 会不会泄密、会不会在用户没同意时干危险的事、权限是不是只给了刚好够用的"。

检查项：

- [ ] 全目录无明文敏感信息：API key / token / 密码 / 账号 / 私有地址
- [ ] 危险操作有显式清单：删除、覆盖、部署、发送消息、联网改状态、付费调用——逐项列出而非笼统一句
- [ ] 每个危险操作带确认门槛：执行前先展示将要做什么，确认后再动手（§6.2 原则三）
- [ ] `allowed-tools` 最小化：只列实际用到的工具；用不到就不写；高危通配属安全问题（§2）
- [ ] 若诊断中发现疑似敏感信息：报告中只描述**类型与位置**，不回显完整值

常见病症与修法：

| 病症 | 症状 | 修法 |
|---|---|---|
| 敏感信息入库 | 硬编码 key / token 随 skill 分发 | 提醒用户确认后删除，或改为配置引用 / 占位符 |
| 危险操作裸奔 | 删除 / 覆盖类步骤无任何确认 | 补硬性确认门槛与禁止默认执行规则 |
| 权限全开 | allowed-tools 放开任意命令执行 | 收敛到实际所需的最小集合 |

## 诊断输出格式

审查完毕，输出按影响排序的问题列表，每条四字段：**维度 / 严重度 / 位置 / 建议**。

```markdown
## 诊断结果：{目标 skill 名}

| # | 维度 | 严重度 | 位置 | 问题与建议 |
|---|------|--------|------|-----------|
| 1 | 触发语义 | 高 | SKILL.md:3 (description) | 触发词全埋正文；建议按 anatomy §5.1 回收 |
| 2 | 安全边界 | 高 | scripts/deploy.py:12 | 删除操作无确认门槛；建议补硬性确认 |
| 3 | 资源组织 | 中 | SKILL.md 全文 | 268 行超限；建议按 §4.2 下沉示例章节 |
| 4 | 工作流可靠性 | 低 | 工作流节 | 步骤无进度勾选；建议补 checkbox（§6.1） |
```

严重度与排序规则（按影响从高到低）：

1. **高**——影响触发、正确性、执行稳定性或安全：触发失败、敏感信息、危险操作缺确认、流程不可执行
2. **中**——影响可维护性与 token 成本：异常分支缺失、结构臃肿、资源组织混乱、依赖不可安装
3. **低**——体验优化项：措辞润色、示例补充、进度追踪改进

## 使用纪律

- 诊断 ≠ 修改：输出问题列表后先给分优先级的优化计划，等用户明确确认再动手
- 用户指定单一方向（如只改 description）时只做该维度深查，其余维度的问题列入"额外建议"，不偷偷扩大改动面
- 每次修改后用 [eval-notes.md](eval-notes.md) 的 before/after 记录法验证，验证失败优先回滚
