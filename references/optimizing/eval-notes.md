# 触发准确性评估 — 轻量方法

> 回答一个问题：**改了 description 之后，触发到底是变好了还是变坏了？** 不靠感觉，靠测试集和记录。配合 [review-checklist.md](review-checklist.md) 维度一使用——清单判断"写得好不好"，本文判断"改完是否真的更好"。
>
> 轻量落地版：不引脚本、不跑子 agent，全部动作是"构造几句话术 → 逐条走查 → 记进表格"，适合个人 skill 库的迭代节奏。

## 一、触发测试集：3 正例 + 1 负例

改任何 description 前先冻结测试集——改完后才有了判断好坏的基准。

### 正例（3 条）：用户真实口吻的变体

- 同一意图的三种说法：一条正式、一条随意、一条口语省略（可含错别字 / 缩写）
- 必须具体、有细节，像真的会打出来的话；不要抽象请求
- 至少 1 条**不点名 skill 名**——用户不会说"用 xx skill"，只会描述自己的问题

好正例："这个 skill 老是不触发，帮我看看 description 哪里不对" 而非 "优化触发"。

### 负例（1 条）：语义相近但应路由给别人

- 最有价值的负例是 **near-miss**：与触发词关键词重叠、但意图应归其他 skill 的话术
- 明显无关的负例没有测试价值——"写个排序算法"测不出 PDF skill 的任何问题
- 例：对 sm-optimizer，"帮我优化这段 Python 代码的性能"含"优化"但应路由给代码类 skill

### 判定

3 正例全触发 + 负例不触发 = 通过；正例失触发 = 触发词问题（回 review-checklist 维度一修写法）；负例误触发 = 边界问题（考虑反触发句或更具体的名词，见 skill-anatomy §5.2 / §5.4）。

## 二、before/after 对比记录

每次优化记一行。学 darwin 的 results.tsv 思想——它用 TSV 追加 keep/revert 记录形成"只进不退"的棘轮；这里用 markdown 表格，贴在会话或笔记里即可：

| 日期 | 改动点 | 预期影响 | 验证话术 | 结果 |
|---|---|---|---|---|
| 08-28 | 触发词从"优化"改为"改 skill / 触发不准" | 正例 2、3 能触发 | 3+1 测试集 | 3/3 触发，负例不触发 → **keep** |
| 08-28 | description 加反触发句"不用于代码优化" | 负例不再误触 | 同上 | 正例 1 失触发 → **revert** |

记录规则（吸收 darwin 棘轮机制）：

- **一次只改一个变量**：一次同时改触发词和工作流，结果好坏无法归因
- **改动前先写预期影响**：写不出预期，说明自己也不信这个改动，别做
- **结果差 → 回滚优先**：恢复上一个 keep 版本，而不是在坏版本上叠加新改动
- 结果列只写 通过/失败 + keep/revert，长篇分析另起段落，不塞进表里

## 三、何时不该优化

- **触发没问题，只是"感觉不放心"** → 不动。没有失败案例（真实会话中的漏触发或误触发）就没有改动依据；凭感觉重写 description 大概率引入新问题
- **改动会破坏已验证行为** → 回滚优先。新 description 让旧测试集的正例失触发，比原问题更糟——已验证的行为是资产
- **连续两轮收益微小** → 停手。darwin 的"见好就收"：触顶信号是停手信号，不是继续信号；硬凑轮数往往只是给 description 加废话
