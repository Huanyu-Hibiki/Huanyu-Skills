# sm-writer 编写工作流 — 访谈、起草、复核三阶段

> 来源：思想吸收自 Matt Pocock 的 [write-a-skill](https://github.com/mattpocock/skills/tree/main/skills/productivity/write-a-skill)（MIT 许可，经 `template/writer/write-a-skill` 派生），按本项目语境重写，非逐字拷贝。
> 用途：sm-writer（④ 编写）起草新 skill 的流程手册。结构判据与设计原理不在本文重复维护，统一见 [skill-anatomy.md](../../shared-references/skill-anatomy.md)；落盘前的逐项自检见 [structure-checklist.md](structure-checklist.md)。

核心是三阶段：**需求收集 → 起草 → 用户复核**。贯穿全程的访谈铁律：**一次一问、选择题优先**——一次抛五个问题，等于一个问题都没问清。

## 1. 阶段一：需求收集

必问四项，问全才动笔：

| # | 必问 | 要弄清的事 |
|---|---|---|
| 1 | 覆盖什么任务域？ | 边界：管什么、不管什么 |
| 2 | 有哪些具体使用场景？ | 80% 场景是哪个——它决定 SKILL.md 的最小工作流 |
| 3 | 要不要脚本？ | 有没有确定性操作（校验 / 枚举 / 渲染 / 统计） |
| 4 | 要不要参考资料？ | 有没有 SKILL.md 装不下的深度细节 |

访谈技巧：

- **一次一问**。问一个，等回答，再问下一个。
- **选择题优先**。"要不要脚本？"不如："这里有个'列出所有超期任务'的操作——A 做成脚本（结果可复现、省 token），B 写成 LLM 指令（灵活但每次生成的代码略有差异）。选哪个？"
- **识别 feature 背后的真问题**。用户说的常是解法而非需求："我要一个能定时扫描的 skill"——追问一句，真问题可能是"每次手动跑太烦"，解法未必是往 skill 里写定时。听到解法式描述时，多问一句"这想解决什么问题？"

## 2. 阶段二：起草

骨架按固定顺序生成——frontmatter 定路由，路由错了内容再好也无人触发：

1. **frontmatter**：name + description。description 按公式（skill-anatomy §5）：第一句做什么（动词 + 具体对象），第二句 `Use when` + 触发词（用户原话）。
2. **工作流**：80% 场景的最小步骤清单，编号 + 勾选框（skill-anatomy §6.1）。一步只说"做什么"，"怎么做"下沉。
3. **边界**：明确不做什么（防误触发）+ 危险操作的确认门槛。

何时需要子目录：

| 信号 | 动作 |
|---|---|
| SKILL.md 超 200 行 | 拆出最大的非核心章节到 `references/<topic>.md`，原地留 1-2 行指针（下沉规则：skill-anatomy §4.2） |
| 存在确定性操作：同样的代码会被反复生成、错误需要显式处理 | 写成 `scripts/` 脚本——省 token，结果可复现 |
| 两者皆无 | 都不建。可选目录按需创建，不预建空目录（skill-anatomy §1） |

## 3. 阶段三：用户复核

- **呈现草案要点，不贴全文**：name、description、工作流步骤概要、建了哪些子目录及为什么。全文是给 Agent 读的，用户要的是决策点。
- **问三件事**：
  1. 这些使用场景都覆盖了吗？
  2. 有缺漏或含糊的地方吗？
  3. 哪部分该更详细、哪部分该更简略？
- **先自检再交用户**：对照 [structure-checklist.md](structure-checklist.md) 逐项过完再请用户复核——别把"description 缺触发词"这种低级问题留给用户发现。
- **确认后才落盘**：写文件是危险操作。展示目标路径与将创建的文件清单，用户点头才动手（skill-anatomy §6.2）。

## 4. 常见坑

| 坑 | 症状 | 纠正 |
|---|---|---|
| description 写成营销文案 | "强大、全面、现代化……" | description 是路由信号不是广告：删形容词，保动词 + 对象 + 触发词（skill-anatomy §5） |
| 上来就写 300 行巨无霸 | SKILL.md 变成完整手册 | 入口只装 80% 场景的最小工作流，细节下沉 references/（skill-anatomy §4）——每次触发都要为全量行数付 token |
| 把确定性操作写成 LLM 指令 | "让 Agent 列出目录并统计……"，每次结果略有差异 | 脚本做确定性事，LLM 做判断事（skill-anatomy §6.2）——可复现的操作交脚本 |
