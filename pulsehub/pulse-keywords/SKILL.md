# pulse-keywords · 三层关键词矩阵

从"用户想要什么"到"我们该覆盖什么词"。

## 三层矩阵模型

> 经过实战验证的分类——每层对应用户不同的决策阶段。

| 层级 | 特征 | 数量 | 用户状态 |
|------|------|------|---------|
| **A. 泛需求词** | 搜索量大、转化泛、用户在迷茫期 | 10 个 | "好像需要做点什么" |
| **B. 精准需求词** | 搜索量小但意图明确、**主战场** | 15 个 | "在找方法" |
| **C. 交易决策词** | 转化率最高、用户在对比 | 10 个 | "准备付费" |

## 何时触发

- 用户说"关键词矩阵""获客关键词""搜索词"
- pulse-insight 完成后，自然衔接

## 项目定制协议（条件执行）

如果《项目档案.md》登记了**定位协议文件**（品牌手册 / IP 对齐 / 内容红线，路径记在档案「定位协议」字段），所有 PulseHub 产物先读取该文件并服从其约束。PulseHub 只负责获客执行（关键词/选题/文案/CTA/私域承接），**不单独发明人设**——受众、母题、调性、产品路径、禁止事项一律以协议文件为准；协议与 PulseHub 默认结构冲突时，协议优先。

**Fallback**：档案未登记协议、或文件不存在 → 跳过本节，按《项目档案.md》自身的定位字段执行。

## 前置

1. **读 `项目档案.md`** 取产品信息 + 目标人群
2. **读 `人群语料库.md`**（pulse-insight 产出）——取搜索行为维度 + 真实搜索词

**Fallback（前置缺失）**：项目档案缺失 → 🛑 先跑 `pulse-init`；语料库是模板态 → 提示先跑 `pulse-insight`，用户说"先出矩阵" → 照常生成但"背后痛点"列全部标 `[待语料校准]`，不冒充真实痛点。

## 工作流

### Step 1 · 生成三层矩阵

**表格列**（每词标注 5 维）：

| 列 | 内容 |
|----|------|
| **关键词** | 具体的词/短语 |
| **类型** | 泛需求 / 精准需求 / 交易决策 |
| **背后需求** | 用户搜这个词时在想什么 |
| **背后痛点** | 引用 `人群语料库.md` 的痛点标签 |
| **适合引流品类型** | 清单 PDF / 对比表 / 教程 / 案例集 / 自查工具 |
| **转化潜力** | ⭐⭐⭐⭐⭐（5 星最值得做） |

**示例**：

| # | 关键词 | 类型 | 背后需求 | 背后痛点 | 引流品 | 转化 |
|---|--------|------|---------|---------|--------|------|
| 1 | "工程合同 怎么看" | 精准 | 想学怎么审合同 | 怕漏条款 | 合同审查清单 PDF | ⭐⭐⭐⭐⭐ |
| 2 | "AI 法律工具" | 泛 | 好奇 AI 能帮什么 | 没时间 | 工具对比表 | ⭐⭐⭐ |
| 3 | "XX 律师 费用" | 交易 | 在对比律师 vs 工具 | 成本敏感 | 费用对比计算器 | ⭐⭐⭐⭐⭐ |

### Step 2 · 标注最值得做的 5 个

用 ⭐ 标注最值得做内容的 5 个词。判断标准：
- 转化潜力高
- 竞争不太激烈（大号没覆盖）
- 有现成的引流品可配套
- 对应 `人群语料库.md` 里频次最高的痛点

**🔴 CHECKPOINT · 用户挑核心词**：矩阵 + ⭐ 建议展示给用户，**用户挑定 ≤5 个核心词**才进 Step 3——验证只验用户挑的词，AI 不代挑。

### Step 3 · 平台验证（默认跑；跳过有代价）

用 PulseHub 工具或 Chrome DevTools 验证关键词在目标平台的真实热度。**当用户要求用 Chrome DevTools，或 RSSHub/静态抓取拿不到小红书、知乎等站内内容时，必须直接打开平台站内搜索页，而不是只看 Bing/搜索引擎结果页。**

```bash
# 小红书搜索热度（RSSHub 可用时）
bash _shared/scripts/shell/rsshub-fetch.sh "/xiaohongshu/search/notes?keyword=你的关键词"

# B站搜索
bash _shared/scripts/shell/rsshub-fetch.sh "/bilibili/search/keyword/你的关键词"
```

路径基准：命令从 PulseHub 仓库根目录执行；`_shared/` 是仓库根的共享脚本目录。RSSHub 不可用 → 用 Chrome DevTools 打开平台站内搜索页人工核对热度。

**Chrome DevTools 验证最低标准**：
- 小红书：记录搜索页可见的笔记标题、作者/日期、互动数、“大家都在搜”。详情页 404/风控时不要编内容，标注“详情不可读”。
- 知乎：记录搜索页的问题标题、回答摘要、相关搜索；能进详情再进详情，403/异常访问时标注边界。
- 论坛/贴吧：直接进站内搜索；若“数据获取失败”或“页面不见了”，记录失败和替代来源。
- 每个被判为“强/很强”的关键词，至少要有 3 条页面可见信号支撑。

### Step 4 · 竞品关键词对比

列出 3-5 个竞品，分析：
- 竞品在覆盖哪些词？
- 有没有他们遗漏但你该做的词？
- 哪些词他们很强，你不必硬碰？

### Step 5 · 写入项目档案

把关键词矩阵追加到 `项目档案.md` 的"内容策略"段落 + 更新索引。

## 人 × 数字员工分工

- **数字员工**：生成三层矩阵、标注 5 维、验证热度、竞品对比

## 注意（不要做）

- **精准转化词 > 核心流量词**——小账号做核心词拼不过大号
- **交易决策词是金矿**——搜这些词的人已经准备付费
- **否定词很重要**——明确"不做什么"比"做什么"更能省时间
- **热度数据要标注来源**——没验证就标"待验证"
- **语料库缺失时不要编**——`人群语料库.md` 还是模板状态 → 先回去跑 `pulse-insight`，不要凭想象填"背后痛点"列
- **验证失败不要硬标热度**——Chrome DevTools 打不开/被风控 → 该词标"待验证"，不要给"强/很强"结论
- Chrome DevTools 站内验证细节见 `references/chrome-devtools-keyword-validation.md`，尤其适用于小红书 / 知乎 / 论坛类关键词验证。
